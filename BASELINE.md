# sqlformat-rs — baseline (upstream, measured on box)

Date: 2026-11-19. Measured by Rustsmith on the box, not copied from the
proposal.

## Environment

- box: Ubuntu 24.04, 2 vCPU (`nproc` = 2), 3,883 MB RAM visible (`free -m`).
- upstream: `sqlparse` 0.6.1, console script `/home/user/.local/bin/sqlformat`
  (216 B shebang wrapper around `sqlparse.__main__:main`), CPython 3.12.
- timing harness: `baseline/run.py` — `subprocess.run` + `time.monotonic()`
  for wall, `resource.getrusage(RUSAGE_CHILDREN).ru_maxrss` for peak RSS of
  the child. No `/usr/bin/time` on the box.

## Workload

`baseline/corpus.sql` — 20,000 single-line SELECT statements, one per line,
generated by `baseline/gen.py` (`random.seed(20261119)`, deterministic).

- bytes: 3,038,894
- lines/statements: 20,000
- sha256 (first 24): `4cf98f934f8ac22eeefb503c`

Shape of one statement (names vary):

```
SELECT id, name, email, region FROM orders WHERE id = 'v42' AND amount > 17 AND note LIKE '%alpha_beta%' ORDER BY created_at DESC LIMIT 100;
```

## Upstream numbers, `sqlformat -r corpus.sql`

Three runs, output to file, compared byte for byte (identical):

| run | wall | peak RSS | output bytes |
|---|---|---|---|
| 1 | 21.91 s | 31,800 KB | 3,578,891 |
| 2 | 21.88 s | 31,732 KB | 3,578,891 |
| 3 | 19.72 s | 31,780 KB | 3,578,891 |

- **median wall 21.88 s**, spread 19.72–21.91 s (±5%).
- peak RSS ≈ 31.8 MB, flat across runs.
- output 3,578,891 B, sha256 (first 24) `c481988a319df7a5b6ce332c`,
  ratio output/input = 1.18.

### vs the number Chief quoted

Chief's baseline was 3.1 MB / 20,000 statements -> **28.30 s**, output
4,895,557 B, RSS 36,652 KB. Same statement count and same input size, but
his output is 1.37x larger, so his corpus produces more line breaks per
statement (more items per select list / more predicates), which is what the
formatter's time is spent on. The two runs are consistent in shape, not in
absolute value; **the acceptance number for this project is ours**
(`BASELINE.md` + `corpus.sql` sha above), his is the sanity check that the
order of magnitude is right.

## CLI surface for the port (verified against `sqlformat -h` on the box)

- `-r`, `--reindent` — reindent statements (the mode we implement).
- `-k {upper,lower,capitalize}`, `--keywords` — keyword case.
- `--indent_width N` — indentation width, default 2. **No short form.**
  Note for Chief: the scope line said `-i/--indent_width`; `-i` is actually
  `--identifiers {upper,lower,capitalize}` (identifier case). The port takes
  `--indent_width` and leaves `-i` out unless told otherwise.
- positional `FILE`, `-` = stdin, `-o FILE` / `--outfile`, `--in-place`.

3. Same gate as xlsx2csv: `fmt --check`, `clippy -D warnings`, `cargo test`,

## Port result (2026-11-19, streamed pipeline)

`target/release/sqlformat-rs -r fixtures/corpus-20k.sql`, three interleaved
runs with `python3 baseline/run.py`:

| tool | wall (3 runs) | median | peak RSS | output |
| --- | --- | --- | --- | --- |
| sqlformat-rs | 1.11 / 1.02 / 1.03 s | 1.03 s | 12,728 KB | 3,578,891 B |
| sqlformat 0.6.1 (CPython 3.12) | 20.29 / 19.27 / 19.76 s | 19.76 s | 31,928 KB | 3,578,891 B |

Same output sha256 `c481988a319df7a5b6ce332c...`. Speedup 19.2x, RSS 0.40x.
Details: `reports/2026-11-19-sqlformat-rs-streaming.md`.

## Re-measure (later session, same corpus, same command)

Same box, same `fixtures/corpus-20k.sql` (sha `4cf98f93…`), `sqlformat -r`
versus `sqlformat-rs -r`, three runs each, outputs compared byte for byte:

| tool | runs (wall) | median | peak RSS |
|---|---|---|---|
| `sqlformat-rs` | 1.585 / 2.009 / 2.104 s | **2.009 s** | 15,104 KB |
| `sqlformat` 0.6.1 | 23.318 / 24.788 / 23.042 s | **23.318 s** | 31,696 KB |

- both outputs: 3,578,891 B, `cmp` clean (`RUST_VS_UPSTREAM_BYTE_IDENTICAL`).
- ratio 11.6x on wall, 0.48x on RSS. The earlier measurement in the section
  above gave 19.2x; the box is shared, so report the range, not one number.
- acceptance floor is 3x: the worst observed pair (11.6x) still clears it.
